## 2. Why the project is here

The active object is the **Advanced Companion / Squad Field Lab**.

The Owner does not want a narrow follower with an ever-growing list of hard-coded behaviors.

The Lab is intended to become a serious manual research / authoring instrument in which the Owner can:

- build and reshape squad geometry;
- manipulate real embodied companions;
- vary causally meaningful group/member dynamics;
- author different responsibility allocations;
- run the same situation repeatedly;
- capture / restore setups;
- compare A/B experiments;
- preserve temporal traces and causal provenance;
- discover useful behavior manually before deciding what, if anything, should become autonomous.

The central loop is still:

`play → manually shape behavior → observe → perturb → compare → discover recurring intent / responsibility → only then consider encoding part of it`.

Do not reverse that loop into:

`invent AI behavior → build demo → ask whether it looks intelligent`.

The Owner explicitly values the Field Lab as a direction **in its own right**, not merely as temporary scaffolding for one autonomous feature.

## 8. Preparation semantics — two important falsifications

### HOLD-only preparation was false

Historical shortcut:

`prepared = HOLD`

was falsified.

A settled independent MOVE at the same material responsibility anchor can support the same takeover capability.

Therefore preparation is represented through an explicit readiness evidence seam rather than the command label.

### Coarse ARRIVED was also too weak

The first readiness seam reused the Trial/display threshold:

`1.35 × slotTolerance`.

A dedicated browser falsifier produced a real false positive:

- display said `MOVE · ARRIVED`;
- target error was about `0.20m`;
- motor-stop tolerance was `0.18m`;
- motor still requested about `0.71` normalized velocity;
- readiness incorrectly said `prepared YES`.

This was a real semantic FAIL.

The correction now binds material settle to:

- `targetError <= slotTolerance`;
- no active requested motor motion.

Stable HOLD and stable MOVE true positives still pass.

The looser ARRIVED band remains a display / Trial classification only.

Read `docs/CURRENT.md §33–34` for the exact evidence and failure history.

## 10. Candidate explicitly rejected before implementation

A naive **moving responsibility / relay** situation was considered after the takeover campaign.

The idea was to let the player move through space while responsibility could transfer between YOU and C1.

Read-only red-team of the existing Combat Micro contract showed:

- APPROACHING: hostile pursues current bearer;
- PRESSURING: hostile stops and pressure clock runs;
- RECOVERING: hostile moves away from the new bearer after STRIKE;
- then returns to APPROACHING;
- the current bearer can break pressure by moving beyond `pressureBreakRange`.

In open space, the simple relay concept is therefore vulnerable to:

> **trivial disengagement / kiting instead of meaningful teammate responsibility.**

Rescuing it through artificial player slowdown, dwell/capture tasks, forced corridors or another pressure objective risks rebuilding the rejected Shared Task geometry/task problem.

Therefore:

> **DO NOT IMPLEMENT THE NAIVE MOVING-RESPONSIBILITY / RELAY IDEA AS THE NEXT STEP.**

This is only a rejection of that naive contract, not of all future moving-responsibility situations.

See `docs/CURRENT.md §35`.
